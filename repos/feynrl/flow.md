FeynRL is the library behind [the P3O paper](#/read/feynrl_paper): a Ray driver that keeps a pool of vLLM rollout GPUs and a pool of DeepSpeed training GPUs busy on RL post-training. This read-through follows one run of its GSM8K example from the command line to the moment new weights reach the rollout engines, first in sync mode and then in overlap (async) mode, and ends with what the unit tests pin down. After it you can say where each number of a run comes from, which code computes the advantage and the loss for GRPO, CISPO, PPO and P3O, and how stale the training data can get.

## What does one training run do? {#overview}
source: main_rl.py:L14-L26 · docs/ARCHITECTURE.md:L18-L37 · examples/llm/README.md:L60-L66

RL post-training of a language model repeats one loop ([L16](#/read/lecture_16) teaches it): sample several completions per prompt, score them, and raise the probability of the ones that scored above their group's average. FeynRL splits that loop across two pools of GPUs. **Rollout engines** run vLLM, a fast inference server, and only generate. **Training engines** hold the model in DeepSpeed ZeRO-3 (parameters, gradients and optimizer state sharded across GPUs) and only compute losses and gradients. A single Python driver process, coordinating both pools through Ray (a library for remote actors), moves data and weights between them.

The run you launch is one line:

`python main_rl.py --config examples/llm/rl/gsm8k/qwen2.5-1.5b-instruct/train_sync.yaml`

Everything after that happens in this order, and each section below is one row.

| Stage | Where in the code | What it produces |
|---|---|---|
| Load and validate the YAML | `main_rl.py` → `configs/load.py` | a checked config object |
| Build engines | `run_rl_sync.main` → `core/rl_engines.py` | 6 training actors, 2 rollout actors |
| Pick prompts | `MixedDatasetSampler` | 512 prompts per epoch |
| Generate | `VLLMRolloutEngine.generate` | 2,048 completions with their log-probabilities |
| Score | `rewards/math_verify_reward_func.py` | a 0/1 reward on each completion's last token |
| Advantage | `Base.normalize_rewards` | a per-prompt z-score on every response token |
| Batch | `prepare_training_batches`, `shard_and_put` | 43 micro-batches per training GPU |
| Loss and step | `GRPO.train_step` (or CISPO, PPO, P3O) | one optimizer step |
| Weight sync | `sync_weights_direct` | rollout engines on the new weights |

One word means something unusual here. A FeynRL **epoch** is one rollout-then-train cycle, not a pass over the dataset. The recipe runs 100 of them.

The driver also keeps an integer **policy version**. It starts at 0 and goes up by one each time training finishes an epoch. Each rollout engine records the version of the weights it has loaded (`loaded_version`), and every completion is stamped with the version that generated it. That integer is FeynRL's way of saying whether data is **on-policy** (generated by exactly the weights being updated) or **off-policy** (generated by older weights, or by an engine that computes probabilities differently). The rest of the read-through keeps asking how far apart those two versions can get.

::code main_rl.py:L14-L26 | the entry point validates the YAML and then picks one of two drivers on a single flag, overlap.enabled
::note warning | The README's command passes `--config`, but the parser defines `--config_file`; it works only because argparse accepts unambiguous prefixes. And `--experiment_id` defaults to `run_1` and overwrites the YAML's `experiment_id` inside `load_and_verify`, so a sync and an async run launched as the README shows both log under `run_1` unless you pass the flag.

## What does one YAML file set? {#recipe}
source: train_sync.yaml:L1-L114 · core/rl_engines.py:L18-L63 · core/rl_engines.py:L362-L376

The example `train_sync.yaml` fine-tunes Qwen2.5-1.5B-Instruct on GSM8K, grade-school math word problems whose answer is a single number. Its sections map one-to-one onto the stages above.

::code train_sync.yaml:L27-L47 | overlap is off; GRPO with a symmetric clip of 0.4, no reference-model KL, no entropy bonus, and one update per full replay buffer
::code train_sync.yaml:L55-L82 | 100 epochs of one training pass; 8 sequences per micro-batch per GPU; 4 samples per prompt at temperature 1; 512 "samples" per epoch, which turn out to be prompts

The run block asks for 6 training GPUs and 2 rollout GPUs, with tensor parallelism 1 (each rollout engine fits on one GPU) and `weight_sync_method: "direct"`.

`train.alg_name` picks the algorithm. The driver looks it up in a registry of five classes (GRPO, CISPO, P3O, PPO and P4O) and passes every training actor the same keyword arguments, so all algorithms read the same config keys.

::code core/rl_engines.py:L18-L24 | alg_name is a key into this table; each value is a module path and a class name
::code core/rl_engines.py:L58-L60 | the one place where overlap mode reaches the loss: use_decoupled_loss is simply overlap.enabled

**How many completions per epoch?** `rollout_samples_per_epoch` counts *prompts*, and the code rounds it up to whole dataloader batches. A batch holds one slice of `rollout_batch_size_per_gpu` prompts per rollout engine: $2 \times 64 = 128$. So 512 prompts make $\lceil 512/128 \rceil = 4$ batches, and with 4 samples each the replay buffer receives $512 \times 4 = 2048$ completions per epoch, an upper bound because empty responses are dropped.

## What does the driver do each epoch? {#sync-loop}
source: run_rl_sync.py:L27-L99 · run_rl_sync.py:L101-L242 · run_rl_sync.py:L339-L470 · docs/ARCHITECTURE.md:L35

With `overlap.enabled: False`, `main_rl.py` hands control to `run_rl_sync.main`. Its setup is a checklist: start Ray and check the cluster has $6 + 2 = 8$ GPUs, create one training actor per training GPU and wait until every one has built its DeepSpeed engine, load the tokenizer, import the reward module named in the YAML, create the rollout engines, build the prompt dataloader and an empty replay buffer.

Then comes the loop over 100 epochs. One epoch is a strict sequence:

::code run_rl_sync.py:L34-L47 | empty the buffer, then block until every rollout engine has finished every batch of the epoch
::code run_rl_sync.py:L68-L90 | shard the buffer once, call run_training_step train_steps_per_epoch times on the same shards, then bump the version once

Back in `main`, the epoch ends with a weight sync, unless it was the last epoch: the trained weights are pushed to the rollout engines so that the next epoch generates with them. If the direct push raises, the driver saves a checkpoint and has every engine reload from disk instead.

Three consequences are worth stating. Rollouts are generated once per epoch, never once per training step: with `train_steps_per_epoch: 3`, the three passes reuse the same micro-batches. The version goes up once per epoch, however many passes it makes. And $N$ epochs give $N - 1$ syncs, 99 here.

::predict sync-epoch-loop
::animation fixture:rollout-train-timeline | in sync mode (s0) the rollout lane is idle for the whole training segment and the training lane for the whole rollout segment; the two never overlap, which is the cost overlap mode removes later
::widget fixture:feynrl--epoch-ledger | raise train_steps_per_epoch to 3: three passes over the same micro-batches, still one version bump, and only the micro-batches before the first optimizer tick are green, meaning they see the weights that generated them

ARCHITECTURE.md calls sync mode "fully on-policy". That holds for the first pass of each epoch, and only up to the engine mismatch discussed under [the loss](#grpo). Once an optimizer step has happened inside the epoch, every later micro-batch is scored by moved weights against log-probabilities stored by the old ones.
::kp sync-epoch-loop

## Where do the prompts come from? {#prompts}
source: core/rl_engines.py:L187-L245 · data_feeds/mixed_sampler.py:L44-L132 · docs/ARCHITECTURE.md:L47

The rollout dataloader is an ordinary PyTorch `DataLoader` whose batches are chosen by `MixedDatasetSampler`. The sampler exists for recipes that mix several datasets with ratios such as `{math: 0.5, code: 0.3, chat: 0.2}`; the GSM8K recipe has one dataset with ratio 1.0, so for it the mixing is trivial. What matters even here is how indices are drawn.

::code core/rl_engines.py:L197-L200 | the dataloader's batch size is engines × rollout_batch_size_per_gpu, and the number of batches is a ceiling division
::code data_feeds/mixed_sampler.py:L80-L90 | fixed per-dataset counts by largest-remainder rounding, computed once
::code data_feeds/mixed_sampler.py:L126-L129 | rng.integers draws indices with replacement

Each batch first decides how many prompts come from each dataset. If there are no more datasets than slots and `dynamic_ratio_every_step` is off, the split is fixed once: multiply the normalized ratios by the batch size, floor each share, and give the leftover slots to the largest fractional parts. Otherwise the counts are redrawn from a multinomial every batch. Then indices inside each dataset are drawn **with replacement**.

::worked mixed-dataset-sampling
::widget fixture:feynrl--mixed-sampler | set the batch size to 7 with ratios 0.5/0.3/0.2: floors give 3/2/1 and the one outlined leftover slot goes to the largest fractional part; tick dynamic_ratio_every_step and the split changes from batch to batch

Sampling with replacement means one epoch does not visit every prompt once. Each epoch draws 512 prompts, some repeated, some never chosen; the dataset size never enters the epoch length. The sampler is reseeded per epoch, so the draws differ from epoch to epoch but are reproducible.
::kp mixed-dataset-sampling

## How do the rollout engines generate? {#rollout}
source: core/rl_engines.py:L108-L185 · core/rl_engines.py:L346-L411 · rollouts/base.py:L8-L64 · rollouts/vllm_engine.py:L302-L490 · docs/ARCHITECTURE.md:L18-L22

`create_rollout_engines` turns rollout GPUs into Ray actors. A model too big for one GPU can be split over `tensor_parallel_size` GPUs (tensor parallelism, TP), so the number of engines is the GPU count divided by TP, rounded down, with at least one. Each actor asks Ray for TP GPUs and builds one vLLM `LLM` inside itself.

::code core/rl_engines.py:L149-L150 | engines = max(1, rollout_gpus // tp): with 2 GPUs and TP 1, two engines; GPUs left over by the floor stay unused

Each epoch, `collect_rollouts` walks the dataloader. Every batch of 128 prompts is cut into one slice per engine (64 each), all engines generate in parallel, and the driver blocks until the slowest returns before adding the results to the buffer.

::code core/rl_engines.py:L378-L403 | shard the batch, fire generate on every engine, block on all of them, append to the replay buffer

Inside the engine, two guards come first. With `force_strict_on_policy: True` (the recipe's setting), the sampling parameters must leave the model's distribution untouched: temperature exactly 1, no top-p or top-k truncation, no stop strings. Each of these changes which tokens get sampled, so the log-probabilities vLLM reports would no longer be the policy's own. The second guard refuses to generate if the engine's loaded weights are not the version the driver says is current.

::code rollouts/base.py:L12-L20 | temperature, top_p and top_k must leave the distribution unchanged, or construction fails
::code rollouts/vllm_engine.py:L318-L321 | strict mode refuses to generate with weights of a different version

The recipe's `stop: ""` and `stop_token_ids: []` pass the "no stop strings" check because the engine's constructor turns empty values into `None` first.

vLLM samples `n_samples = 4` completions per prompt with `logprobs=1`, which makes it return the log-probability of every token it sampled. Those numbers are stored with the sample as **`old_logprobs`**. The trainer never recomputes them; they are the denominator of every importance ratio later.

They are stored **prediction-aligned**. In a causal language model the logit at position $t$ predicts the token at $t+1$, so response token $j$, at index `prompt_len + j` in the full sequence, is predicted at position `prompt_len + j - 1`. The engine writes masks, log-probabilities, rewards and advantages at those shifted positions, so the trainer can line them up with its logits without any index arithmetic.

::code rollouts/vllm_engine.py:L436-L441 | the shift by one: response tokens are written starting at prompt_len − 1
::predict rollout-engine-generate
::widget fixture:feynrl--pipeline-sizes | set run.rollout_gpus to 8 and rollout.tensor_parallel_size to 4: two engines of four GPUs each; at 3 GPUs and TP 2 the readout reports one GPU unused
::note aside | `batch_invariant: True` gives every engine the same seed and sets vLLM's batch-invariant mode, so a prompt yields the same completion whichever engine or batch it lands in. It makes runs reproducible across engine counts; it does not make vLLM's probabilities equal to the trainer's.
::kp rollout-engine-generate

## How is a completion scored, and what is its advantage? {#rewards}
source: rewards/gsm8k_reward_func.py:L19-L50 · rewards/math_verify_reward_func.py:L128-L175 · rollouts/base.py:L121-L183 · rollouts/vllm_engine.py:L355-L494 · rollouts/replay_buffer.py:L44-L97

**The reward contract.** A reward module is a Python file in `rewards/` with a `compute_score(prompt_data, response_data)` function, imported by the name in `reward.reward_func`. It returns three things: a float tensor with one entry per response token, a flag `is_per_token`, and a `correct_threshold` (a completion counts as correct for pass@k metrics when its reward is above it). The simplest module shows the convention: everything is zero except the last token, which gets 1 if the answer after `####` matches the reference.

::code rewards/gsm8k_reward_func.py:L39-L50 | a tensor of zeros the length of the response, and the scalar score written to r[-1]
::code rollouts/base.py:L174-L181 | a plain float is wrapped in a one-element tensor and then fails the length check

The recipe actually uses `math_verify_reward_func`, which follows the same contract but compares answers symbolically with the math-verify package, in a pool of 8 worker processes so the 256 completions an engine returns are verified concurrently.

::predict reward-interface

**The advantage is computed here, at rollout time.** As soon as a prompt's 4 completions are scored, `normalize_rewards` turns their rewards into z-scores within that group: subtract the group mean, divide by the group's standard deviation plus $10^{-8}$. This is GRPO's group baseline ([L16](#/read/lecture_16)).

::code rollouts/base.py:L131-L155 | group mean and Bessel-corrected std; a group of one keeps its raw reward; the z-score goes on the last token and, with broadcast, on every response token

::worked group-relative-advantage

Two choices in that code matter. The standard deviation divides by $n - 1$, not $n$. And `reward.broadcast: True` copies the last token's z-score to every response token, so all tokens of a completion share one advantage. A group where all four answers are right (or all wrong) gets z-scores of exactly 0 and contributes nothing to the policy gradient.

::note slip | [The P3O paper's](#/read/feynrl_paper) Eq. 3 normalizes with the population standard deviation (divide by $n$), which for rewards $(1, 0, 0, 0)$ gives advantages $1.73$ and $-0.58$. The code divides by $n - 1$ and stores $1.5$ and $-0.5$. Same signs, same ranking, advantages smaller by a factor $\sqrt{3/4} = 0.87$ at $n = 4$.

::widget fixture:feynrl--group-zscore | type a 2-token response with reward 0.5 0.5: the group mean uses its sum, 1.0, but the z numerator reads only the last token, 0.5, and the readout flags the mismatch; put the whole score on r[−1] and they agree

The stored z-score is what GRPO, CISPO and P3O read as the advantage. Training micro-batches mix completions from many prompts and never renormalize, so the grouping lives only here.

**What reaches the buffer.** `add_batch_seqs` keeps the prediction-aligned fields and the version stamp, and skips two kinds of sample: empty responses, and any sequence whose prompt plus response is longer than `data.max_seq_len`.

::code rollouts/replay_buffer.py:L73-L82 | over-length sequences are skipped with continue, not truncated, despite the printed message

::note warning | The recipe sets `max_tokens: 1024` and `max_seq_len: 1024`, so any completion that runs to the generation limit makes prompt + response longer than 1,024 and is dropped from training, after it has already entered its group's mean and standard deviation. Its three siblings keep advantages computed partly from it. The code's own message suggests lowering `max_tokens` or raising `max_seq_len`.
::kp reward-interface
::kp group-relative-advantage

## How does the buffer become micro-batches and one optimizer step? {#batching}
source: core/rl_engines.py:L446-L535 · algs/GRPO/grpo.py:L230-L438 · algs/RL/common.py:L213-L239 · configs/load.py:L385-L417 · algs/GRPO/README.md:L12

The replay buffer now holds 2,048 completions, each with its token ids, mask, `old_logprobs`, z-scores and version. `prepare_training_batches` shuffles the whole buffer uniformly and cuts it into micro-batches of `train_batch_size_per_gpu = 8`: 256 of them.

ZeRO-3 shards the parameters, so every forward pass is a collective in which all training GPUs take part. If one GPU ran out of micro-batches before the others, the rest would wait for it forever. So the count is padded up to a multiple of the number of engines by repeating the last micro-batch, and `shard_and_put` deals them out round-robin: engine 0 gets micro-batches 0, 6, 12, …, engine 1 gets 1, 7, 13, ….

::code core/rl_engines.py:L469-L482 | pad by repeating the last batch, because unequal shards deadlock ZeRO-3 collectives

::predict replay-batching
::widget fixture:feynrl--pipeline-sizes | slide the prompts back to the recipe's 512 and read the micro-batch columns: 43 per training engine, with two orange cells, the repeats of the last batch; set training GPUs to 8 and the padding disappears because 256 divides evenly

Inside each training actor, `GRPO.train_step` shuffles its 43 micro-batches with a seed of its own and loops over them: forward pass, loss, backward. With `update_after_full_replay: True` the gradient-accumulation boundary is the last micro-batch only, so gradients pile up over all 43 and DeepSpeed applies the optimizer once. `policy_engine.step()` is called after every micro-batch, but DeepSpeed only steps the optimizer at a boundary.

::code algs/GRPO/grpo.py:L301-L307 | with full replay the only boundary is the last micro-batch

**The denominator.** A per-micro-batch mean would weight a token in a short micro-batch more than a token in a long one, and RL response lengths change every epoch. With `normalize_loss: True`, each actor counts its valid tokens, all GPUs sum the counts, and every micro-batch's raw loss sum is divided by that global count. The extra factor `dp_scale` (gradient-accumulation steps × world size, $1 \times 6$ here) cancels the averaging DeepSpeed does on its own across steps and GPUs, so in the end every valid token in the buffer counts equally.

::code algs/GRPO/grpo.py:L380-L386 | each micro-batch's loss sum × dp_scale / global token count, adjusted for tokens lost to NaN masking

Put the numbers together: 100 epochs × 1 pass × 1 optimizer step = **100 optimizer steps** for the whole run, each over 2,048 completions. The config loader computes the learning-rate schedule from the same count: warmup for $\lfloor 100 \times 0.1 \rfloor = 10$ steps, then cosine decay from $10^{-5}$ to 10% of it.

::code configs/load.py:L388-L389 | with update_after_full_replay there is exactly one optimizer step per training pass, so the scheduler's total is epochs × passes
::kp replay-batching

## What does GRPO's loss compute on one micro-batch? {#grpo}
source: algs/RL/common.py:L38-L84 · algs/GRPO/grpo.py:L105-L228 · algs/GRPO/grpo.py:L310-L369 · algs/GRPO/README.md:L42 · algs/GRPO/README.md:L86-L97

The forward pass returns, for every position, the log-probability the current model gives to the token that actually comes next. `policy_forward` drops the last logit and the first token so that both line up with the prediction-aligned data from the buffer. The log-softmax and the gather of the target token are fused into one compiled kernel, so the full `[batch × length × vocabulary]` log-probability tensor is never stored.

::code algs/RL/common.py:L59-L64 | logits[:, :-1] against input_ids[:, 1:]: the same one-token shift the rollout engine used
::code algs/GRPO/grpo.py:L316-L318 | the advantage is the stored zscore; old_logprobs are vLLM's; nothing about the group is recomputed

**The importance ratio.** The completions were sampled by the rollout engine's weights, call that policy $\pi_{old}$, but the gradient is taken for the current policy $\pi$. Importance sampling corrects for the difference by weighting each token with $r = \pi(a \mid s) / \pi_{old}(a \mid s)$ ([the P3O paper](#/read/feynrl_paper) derives it). Both policies are stored as log-probabilities, so the code subtracts and exponentiates.

::worked supp-importance-ratio

**The clipped surrogate.** GRPO's policy term is PPO's: take the smaller of $r A$ and $\operatorname{clip}(r, 1-\epsilon_\ell, 1+\epsilon_h) A$, sum over valid tokens, negate. The code calls the result `pi_sum`.

$$ \mathcal{L}_\pi = -\sum_{t \in \text{mask}} \min\big(r_t A_t,\ \operatorname{clip}(r_t, 1 - \epsilon_\ell, 1 + \epsilon_h) A_t\big), \qquad r_t = e^{\log\pi_t - \log\pi_{old,t}} $$

::code algs/GRPO/grpo.py:L169-L176 | the log-ratio in float32, zeroed on padding before the exponential so that inf × 0 never makes NaN; then torch.minimum of the two surrogates
::code algs/GRPO/grpo.py:L188-L196 | total = policy term − entropy bonus + KL penalty; clipfrac counts tokens whose ratio left the band

With the recipe's clip of 0.4 the band is $[0.6, 1.4]$. Where the clamped branch wins, the term is a constant times $A$: its value is not zero, but its gradient is, so the token drops out of the update. That happens only on the side the advantage pushes toward: above 1.4 for $A > 0$, below 0.6 for $A < 0$ ([the P3O paper](#/read/feynrl_paper) works through both cases). The function returns a raw sum; dividing by the global token count happens in `train_step`, as above.

::predict grpo-clipped-loss
::widget fixture:ratio-clip | slide the ratio past 1 + clip with a positive advantage: the loss curve goes flat, gradient exactly zero; on the other side of 1 it keeps its slope
::widget fixture:feynrl--clip-loss | select token 1 and drag its log π upward until the ratio leaves the shaded band: the readout switches to the clamped branch, its term stays at clamp·A, and its gradient becomes 0

**What this means for the recipe.** Combine this with the [batching section](#batching). There is one optimizer step per epoch, after the last micro-batch, so every micro-batch of the pass is scored by the same weights that the rollout engines used to generate it. On paper every ratio is 1, the clip never binds, and the gradient is $A\,\nabla\log\pi$: REINFORCE with a group baseline. What keeps ratios from being exactly 1 is the engine gap. vLLM and the HuggingFace model compute the same distribution with different kernels, and `approx_kl` and `clipfrac` in the logs measure exactly that gap. The clip starts doing its trust-region job only when a configuration makes the weights move inside an epoch: more than one pass, or `update_after_full_replay: False`.

::predict supp-on-off-policy
::note why | This is the paper's third source of off-policy data, engine mismatch, showing up in FeynRL's own default recipe. It is also why `clipfrac` is worth plotting even in sync mode: a non-zero value on the first pass of an epoch can only come from the two engines disagreeing.
::kp supp-importance-ratio
::kp grpo-clipped-loss
::kp supp-on-off-policy

## What changes for CISPO, PPO and P3O? {#other-losses}
source: algs/CISPO/cispo.py:L128-L175 · algs/CISPO/README.md:L3-L30 · algs/PPO/ppo.py:L141-L227 · algs/PPO/ppo.py:L421-L464 · algs/P3O/p3o.py:L107-L223

Switching `alg_name` swaps the class the training actors are built from. Everything before the loss stays the same: the same buffer, the same micro-batches, the same forward pass. Each class differs in `compute_policy_loss`, and PPO also in where its advantage comes from.

**CISPO** keeps the clip but uses it differently. The clipped ratio becomes a *detached weight* (`.detach()` stops gradients from flowing through it) on $\log\pi$:

::code algs/CISPO/cispo.py:L171-L175 | clamp(ratio).detach() × log π × A: a weighted policy gradient, not a min over surrogates

Inside the band, CISPO and GRPO give the same gradient value at that point, $r A \nabla\log\pi$. Outside it they part ways. GRPO's gradient is zero on the side the advantage pushes toward; CISPO's is $\operatorname{clip}(r) A \nabla\log\pi$, bounded but never zero. Every valid token keeps contributing.

::predict cispo-vs-ppo-clip
::widget fixture:feynrl--clip-loss | switch train.alg_name between grpo and cispo: the solid GRPO gradient curve drops to 0 past the band on the advantage's side, while the dashed CISPO curve stays at −clamp(ratio)·A on both sides and never touches 0

**PPO** uses the same min-clip surrogate as GRPO, but not the same advantage. It loads a second network, a value model that predicts the expected reward from each prefix, and before the first update of the pass computes generalized advantage estimates (GAE) from the buffer's raw rewards. GAE propagates the final reward backward through the tokens, discounted by `gamma` and smoothed by `tau`. The advantages are then normalized over all valid tokens on all GPUs, and the value model gets its own squared-error loss.

::code algs/PPO/ppo.py:L211-L225 | the GAE recursion, run backward over the response; done stops bootstrapping at the last token
::code algs/PPO/ppo.py:L439-L459 | PPO reads mb['rewards'], the raw reward, not the stored zscore, then normalizes advantages globally across ranks

So the z-score computed at rollout time is unused by PPO. The recipe's `tau`, `gamma` and value-model keys are null; a PPO run has to set them, and the class asserts that it has.

**P3O** is the objective of [the P3O paper](#/read/feynrl_paper), and that read-through explains it; here is where each piece lives. The ratio is the same $\pi/\pi_{old}$. `calculate_ess` sums $\sum w$, $\sum w^2$ and the token count over the micro-batch's valid tokens, all-reduces them across GPUs, and returns the normalized effective sample size $e_\mathcal{B} = (\sum w)^2 / (n \sum w^2)$ as a Python float, which detaches it. The ratio is then capped at $e_\mathcal{B}$ and used as a detached weight, as in CISPO, and a KL term toward the behavior policy is added with weight $1 - e_\mathcal{B}$.

::code algs/P3O/p3o.py:L192-L208 | ratio, ESS, behavioral KL against old_logprobs, and rho = clamp(ratio, 0, ess_factor) as a detached weight on log π
::code algs/P3O/p3o.py:L223 | the total adds (1 − ess_factor) × the behavioral KL; at ESS 1 that term vanishes

In the sync recipe P3O behaves like the others for the reason given in the last section: with ratios near 1 the ESS is near 1, the cap barely binds and the extra KL weight is near 0. P3O becomes different only when ratios spread.

::note aside | P3O still accepts `clip_low` and `clip_high`, but only to report `clipfrac`, the share of tokens a PPO band would have clipped. The fifth registry entry, P4O, is not traced here.
::kp cispo-vs-ppo-clip

## When is a reference model loaded, and what KL does it add? {#kl-ref}
source: algs/GRPO/grpo.py:L90-L103 · algs/GRPO/grpo.py:L343-L351 · algs/RL/common.py:L120-L139 · algs/RL/README.md:L21-L27 · configs/load.py:L779-L783

Many RL recipes add a penalty that keeps the policy close to a frozen copy of the starting model, the reference model ([L16](#/read/lecture_16)'s per-token KL penalty). In FeynRL that costs memory and a second forward pass per micro-batch, so it is strictly opt-in. The reference model is loaded only if `model.ref_model` is set *and* `kl_coeff > 0`, and the config validator rejects either one without the other.

::code algs/GRPO/grpo.py:L98-L101 | no reference path or kl_coeff 0: no reference model in memory at all

When it is on, `ref_forward` runs under `no_grad`, and the KL at each sampled token is estimated with the low-variance "k3" estimator: with $u = \pi_{ref}/\pi$, the per-token value is $u - \log u - 1 = \log(\pi/\pi_{ref}) + \pi_{ref}/\pi - 1$. It is never negative and is zero exactly where the two models agree. The exponent is clamped to $[-10, 10]$ so that one extreme token cannot overflow.

::code algs/RL/common.py:L131-L138 | log-ratio plus exp(clamped reverse log-ratio) minus 1, in float32

For example, a token with $\log\pi = -0.1$ and $\log\pi_{ref} = -0.15$ has log-ratio $0.05$ and $u = e^{-0.05} = 0.95123$, so the estimate is $0.05 + 0.95123 - 1 = 0.00123$.

::predict kl-reference-penalty
::widget fixture:grpo--kl-estimators | FeynRL's compute_kl_distance is the k3 curve: it stays non-negative everywhere and touches 0 only where π = π_ref, unlike the plain log-ratio k1
::note aside | The same estimator, applied to the current policy against `old_logprobs`, gives the logged `approx_kl` (a diagnostic, not a loss term) and P3O's behavioral KL (a loss term).
::kp kl-reference-penalty

## How do new weights reach the rollout engines in sync mode? {#weight-sync}
source: core/rl_engines.py:L537-L612 · rollouts/vllm_engine.py:L215-L300 · rollouts/weight_sync.py:L33-L60 · run_rl_sync.py:L411-L470 · docs/ARCHITECTURE.md:L26-L30

After the optimizer step, the trained weights live as ZeRO-3 shards spread over 6 GPUs, and the rollout engines still hold version $v$. FeynRL has three ways to move them: NCCL broadcast (overlap mode only), direct, and disk. The recipe uses **direct**:

::code core/rl_engines.py:L537-L546 | gather the full state dict from the training engines, then push it to every rollout engine

1. **Gather.** Every training actor calls `gather_state_dict`; it is a ZeRO-3 collective, so all ranks must take part even though only rank 0's result, the full set of parameters on CPU, is used.
2. **Put.** The driver stores that dict in Ray's shared-memory object store and passes a reference to each rollout engine.
3. **Load.** vLLM fans a call out to all of an engine's TP workers through `collective_rpc`, but serializes the arguments with a format that cannot encode payloads over 4 GB. So the engine pickles the weights to `/dev/shm`, a RAM-backed file system, and sends each worker only the file path. Each worker reads the file and calls vLLM's `load_weights`.
4. **Verify.** Each TP worker returns how many parameters it loaded. All zero, some zero, or unequal counts raise an error; a partial load would leave TP shards on different versions.
5. **Finish.** The engine sets `loaded_version` to the new version and resets vLLM's prefix cache, which would otherwise serve attention keys and values computed by the old weights.

::code rollouts/vllm_engine.py:L244-L256 | pickle to /dev/shm and pass a ~50-byte path through collective_rpc; the file is removed in finally
::code rollouts/vllm_engine.py:L284-L293 | advance loaded_version, then invalidate the prefix cache or abort

If any step raises, `main` catches it, saves a disk checkpoint and calls `refresh_rollout_engine`, which makes every engine reload the model from that directory. The run continues either way; only the time per epoch changes. Checkpoints are also saved every `checkpoint_save_interval = 15` epochs and after the last one.

::code run_rl_sync.py:L417-L433 | try direct; on any exception log a warning and fall through to the disk path
::code run_rl_sync.py:L443-L445 | the disk path runs when no sync succeeded, unless it is the last epoch

::predict weight-sync-direct
::widget fixture:feynrl--epoch-ledger | type 150, 0 as the TP results and pick the failing epoch: that epoch's sync raises, the ledger marks a disk save and refresh in orange, and the next epoch proceeds on the right version
::note slip | ARCHITECTURE.md points to `configs/load.py:684-686` for the rule that rejects `nccl` in sync mode; at this commit the check is at L722-L724. Sync mode cannot use NCCL because the plain vLLM engine has no receive path for it.
::kp weight-sync-direct

## What changes in overlap mode? {#overlap}
source: train_async.yaml:L1-L30 · run_rl_async.py:L54-L220 · run_rl_async.py:L625-L947 · rollouts/vllm_engine_async.py:L520-L580 · docs/ARCHITECTURE.md:L37

In sync mode each pool sits idle while the other works. `train_async.yaml` differs from the sync file in exactly two settings that matter, `overlap.enabled: True` and `weight_sync_method: "nccl"`, and `main_rl.py` then imports `run_rl_async` instead.

The machinery is a pipeline. A producer thread in the driver keeps a bounded **prompt queue** filled with shards (a shard is one engine's 64-prompt slice), cycling through the dataloader forever. Each rollout engine runs a **pull loop**: take a shard, submit it to vLLM, post-process the previous one, put its 256 samples on a **results queue**, repeat. Every sample is stamped with the version the pull loop was launched with. Generation never waits for training.

The driver loop is a sequence of **rounds**, the async counterpart of an epoch:

1. Drain the results queue into the replay buffer until one dataloader pass worth of new shards has arrived (4 batches × 2 engines = 8 shards here).
2. Evict items that are too stale (next section).
3. Build micro-batches from the *whole* buffer, as in sync mode, and train `train_steps_per_epoch` passes on them.
4. Bump the version and sync weights inline (the section after next).

Meanwhile the engines keep generating with the old weights, so the shards that arrive during training are one version behind by the time the trainer reads them. That gap is the off-policy data overlap mode trades for throughput.

::animation fixture:rollout-train-timeline | from s0 to s1 the rollout lane stops waiting: it keeps generating while training runs and pauses only for the sync; at s2, with max_lag = 2, the buffer may hold three policy versions at once

One difference from sync mode is easy to miss: the async buffer is **never reset**. It is a deque (a queue with a maximum length) of one pass of completions per unit of `max_lag`, and items leave it only by falling off the full end or by eviction.

::code run_rl_async.py:L840-L847 | after training: bump policy_version, then perform_inline_sync unless this is the last round

### The decoupled loss

Once the buffer mixes versions, "the policy that generated this token" differs from token to token, and a clip on $\pi/\pi_{old}$ mixes two jobs: limiting how far this update moves, and correcting for data that came from somewhere else. So overlap mode switches GRPO, CISPO and PPO to a **decoupled loss** automatically (`use_decoupled_loss = overlap.enabled`, shown [earlier](#recipe)). Before the first optimizer step of each round, the trainer runs one extra no-gradient forward pass over its micro-batches and stores the log-probabilities as a **proximal** snapshot $\pi_{prox}$. Then:

- the clip is applied to $r_{prox} = \pi/\pi_{prox}$, which measures only this round's movement;
- the clipped surrogate is multiplied by a detached behavior weight $w = \pi_{prox}/\pi_{old}$, which corrects for the version gap, capped at `behave_imp_weight_cap = 5`.

::code algs/GRPO/grpo.py:L145-L159 | r_prox for the clip, behave_w = exp(prox − old) clamped to the cap, multiplied into the min-surrogate
::code algs/RL/common.py:L326-L332 | the snapshot is taken once, on the first train_step of the round, before any optimizer step

::predict decoupled-loss-prox
::widget fixture:feynrl--clip-loss | tick "decoupled loss": a log π_prox column appears, the shaded band now sits around π/π_prox, and the readout multiplies each term by w = π_prox/π_old; untick the cap and token 1's w grows past 5

Apply this to the recipe. With one optimizer step per round at the very end, the snapshot is taken with exactly the weights every micro-batch is later scored by, so $r_{prox} = 1$ up to numerical noise between two forward passes. The band never binds, and the decoupled GRPO loss reduces to $-w A$ with gradient $w A \nabla\log\pi$. The whole off-policy correction is the capped weight $w$. P3O ignores the decoupled flag and computes its ratio and ESS against `old_logprobs` directly; [the P3O paper](#/read/feynrl_paper) argues that one loss can serve both modes for this reason.

::note aside | The README for GRPO says the original decoupled-PPO paper builds $\pi_{prox}$ as a running average of parameters; FeynRL substitutes a log-probability snapshot taken at the start of the round. The async engine also relaxes the strict on-policy guard: it allows a gap of one version between the stamp and the loaded weights, because a queued weight update may land before a generate call reads the version.
::kp decoupled-loss-prox

## How stale can the data get? {#max-lag}
source: run_rl_async.py:L222-L251 · run_rl_async.py:L700-L720 · rollouts/replay_buffer.py:L18-L42 · rollouts/replay_buffer.py:L272-L288 · configs/load.py:L810-L820 · docs/ARCHITECTURE.md:L37

`overlap.max_lag` is FeynRL's staleness budget. It acts twice.

**It sizes the buffer.** The deque's maximum length is one dataloader pass of completions times `max_lag`. A pass is the prompt count rounded up to whole batches, so $\lceil 512/128 \rceil \times 128 = 512$ prompts, times 4 samples: 2,048 items per unit of lag. When the deque is full, each new item pushes the oldest one out (first in, first out).

::code run_rl_async.py:L236-L239 | prompts per pass rounded up to the batch boundary, × n_samples × max_lag

**It evicts by version.** After each round's drain and before training, every item stamped below `policy_version − max_lag` is removed.

::code run_rl_async.py:L700-L705 | keep items whose policy_version ≥ policy_version − max_lag

Write $m$ for `max_lag`. With trainer version $T$, the survivors carry versions $T - m$ through $T$: that is $m + 1$ distinct versions, not $m$. With `max_lag: 1` the buffer mixes two versions, so overlap mode is never on-policy, and items of the current version are off-policy too as soon as the round's first optimizer step has happened. A value below 1 is rejected by the config loader before anything starts; there is no code path for a buffer of capacity 0.

::predict staleness-budget-max-lag
::animation fixture:feynrl--overlap-rounds | from round 2 the buffer holds shards older than the trainer; at s3 a failed sync leaves the rollout tag on v1 while the trainer moves to v2, so new shards keep the old stamp; at s6 the full deque pushes the oldest shards out, and at s7 evict_stale drops exactly the shards stamped below v4 − 2 = v2

Which of the two rules binds depends on speed. If rollout is faster than training, the deque fills in fewer than `max_lag` rounds and FIFO removes items before they are old enough to be evicted, so the real lag stays below the budget. If training is faster, the round waits for fresh shards and the overlap buys no speed, but the bound holds. The driver logs `lag_max`, `lag_mean` and the number of distinct versions in the buffer every round, so you can see which regime a run is in.

::note slip | Two comments in `run_rl_async.py` say that at version $T$ the buffer holds versions $T - N + 1$ to $T$, i.e. $N$ versions. The eviction code keeps $T - N$ to $T$, $N + 1$ versions, and a later comment in the same file ("unique_versions up to K+1") agrees with the code.
::kp staleness-budget-max-lag

## How are weights synced in overlap mode? {#nccl}
source: run_rl_async.py:L490-L624 · core/rl_engines.py:L640-L810 · rollouts/weight_sync.py:L100-L210 · algs/RL/common.py:L1170-L1222 · configs/load.py:L703-L730

Overlap mode requires `weight_sync_method: "nccl"`; the validator rejects anything else. NCCL is NVIDIA's library for collective operations between GPUs, and a broadcast sends one tensor from one rank to all others. At startup FeynRL builds a dedicated process group for weight sync, separate from DeepSpeed's: training rank 0 is rank 0, and every TP worker of every rollout engine gets its own rank after it. So the group's size is $1 + \text{engines} \times \text{TP}$, 3 in the recipe.

::code core/rl_engines.py:L653-L654 | world_size = 1 + num_rollout_engines × tp_size
::code rollouts/weight_sync.py:L115-L116 | a TP worker's rank is its engine's offset plus its own TP rank

`perform_inline_sync` runs right after the version bump, in three phases.

1. **Stop and gather.** Stop the producer, empty the prompt queue and push one stop marker per engine. Start the ZeRO-3 gather on the training actors *at the same time* as waiting for the pull loops to finish their in-flight shards, so the two waits overlap. Samples that finish during this window still enter the buffer, stamped with the old version.
2. **Broadcast.** Dispatch a receive call to every engine, then the broadcast on training rank 0. Every TP worker receives every full tensor, and vLLM's `load_weights` slices out its own shard locally.
3. **Finalize.** Each engine reports whether it loaded the expected number of parameters. A tensor containing NaN or infinity is skipped but the engine keeps receiving, so the collective still completes; finalize then reports a partial load.

::code run_rl_async.py:L519-L525 | stop the producer, drain and push stop markers, and fire the gather without waiting for it
::code rollouts/weight_sync.py:L191-L200 | a corrupted tensor is recorded and skipped, never loaded, and the loop goes on
::code core/rl_engines.py:L769-L774 | any engine short of the full count fails the sync, so the rollout version is not advanced

Only a fully successful sync advances `rollout_policy_version`. After a non-fatal failure the engines restart their pull loops on the old weights, new samples keep the old stamp, the lag grows by one, and the next round retries. A fatal NCCL error aborts the run; there is no disk fallback in overlap mode.

::predict weight-sync-nccl-async
::widget fixture:feynrl--pipeline-sizes | tick overlap and set 4 rollout GPUs at TP 2: two engines, ranks 1–2 and 3–4, world size 5
::note warning | The example `train_async.yaml` leaves `nccl_sync_backend: "gloo"`, so its "NCCL broadcast" actually runs the CPU branch of the same three-phase protocol: `torch.distributed.broadcast` into CPU buffers over gloo. ARCHITECTURE.md's "zero-copy" description applies only with the `nccl` backend.
::kp weight-sync-nccl-async

## What do the unit tests check? {#tests}

What they do not cover is as informative:

- **No P3O test.** `calculate_ess` and the capped loss, the algorithm the paper is about, have no unit test.
- **No test that a clipped token's gradient is zero.** The extreme-ratio tests check loss values only, and the gradient tests run at ratio 1, inside the band. The difference between GRPO and CISPO past the band, the point of the [CISPO comparison](#other-losses), is never asserted.
- **The decoupled branch is untested.** Every loss test builds its object with `use_decoupled_loss=False`, so the code path that overlap mode switches on never runs under test.
- **No test of the advantage.** `normalize_rewards` (group mean, Bessel std, broadcast, alignment) and `prepare_training_batches` (padding to equal shards) are exercised only by real runs.
- **The integration test re-implements the formula.** `test_grpo_step.py` trains a tiny model for one step, but writes the clipped loss inline instead of calling `GRPO.compute_policy_loss`, so it checks PyTorch, not FeynRL's loss.
- **The truncation test covers the wrong path.** `test_replay_buffer_max_seq_len_truncation` calls `add()` directly, which truncates. The pipeline enters through `add_batch_seqs`, which drops over-length sequences before `add()` is reached (the [rewards](#rewards) warning).

::note warning | Every test file that imports the PPO class (`test_gae.py`, `test_ppo_loss.py`, `test_ppo_init.py` and three more) fails at collection on Python 3.9, because `ppo.py` uses the `torch.Tensor | None` annotation syntax, which needs Python 3.10 or newer. The test instructions do not name a Python version.

That closes the trace. One epoch of the recipe, end to end: 512 prompts drawn with replacement, 2,048 completions from two vLLM engines with their log-probabilities, a 0/1 reward on the last token, a group z-score copied to every token, 43 micro-batches per training GPU, one optimizer step, and a pickle through `/dev/shm` to each engine. Overlap mode keeps the same loop and moves the costs around: generation never stops, the buffer mixes `max_lag + 1` versions, and the loss acquires a behavior weight. Which loss copes best with that mix is the question [the P3O paper](#/read/feynrl_paper) asks.
